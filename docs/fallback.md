# 模型兜底（2026-07-21）

> 与 [scheduling.md](./scheduling.md) 的「如实透传」原则的关系：网关**依然**
> 不压缩、不截断、不改写、不排队、不预检，过载依然如实透传。兜底是唯一的
> 例外，且严格限定在**节点故障**——请求本身的错误（含上下文超限与 429 过载）
> 一律照旧透传。判定边界见下节，实现见 `backend/app/proxy/fallback.py`。

管理员在「后台 → 模型管理 → 编辑模型 → 启用兜底模型」为某个模型指定一个
兜底目标；该模型的节点出故障时，网关自动改用兜底模型出结果，用户无感。

## 一、什么算「模型出错」

网关已在自己这一层做完鉴权、模型解析、限流。所以上游返回的错误都不是网关的
错，但也不都是模型的错。判据只有一条：**换个模型能不能救活这次请求**。

| 类别 | 信号 | 处置 | 计入熔断统计 |
|---|---|---|---|
| **A · 节点故障** | `ConnectError` / `ConnectTimeout` / `ReadTimeout` / `RemoteProtocolError` / `ReadError`；上游 5xx；2xx 之外的非 JSON 响应 | **触发兜底** | 分子 + 分母 |
| **B · 平台配置故障** | 上游 401 / 403 / 404 | **触发兜底** | 分子 + 分母 |
| **C · 请求本身有问题** | 上游 400 / 413 / 422（含上下文超限）、429；网关自身的 401/403/429 | **如实透传，绝不兜底** | 都不进 |
| — | 2xx | 正常返回 | 仅分母 |

**为什么 401/403/404 算故障**：客户端的鉴权早在网关做完了，上游再回 401 或
404，必然是该节点的 API key 或 `model_api_name` 配错——对用户就是纯故障，
换模型能救。

**为什么 429 不兜底**：一是与「过载如实透传、饱和判定权归引擎」的既定原则
一致；二是 A 模型过载时把全量流量涌向 B，很可能把 B 也压垮，形成级联。429
只透传给客户端，由客户端按 `Retry-After` 退避。

**为什么 C 类不进熔断统计**：进分母会稀释失败率、让熔断变迟钝；进分子会因为
用户乱传参数而误伤一个健康的模型。两头都不沾才正确。

## 二、两层生效

### 第 1 层 · 请求级即时切换

当次请求对用户无感地救回来。**硬边界：只在尚未向客户端发出任何字节时可切。**

所有中继路径（`chat.py` / `common.py` / `anthropic.py` / `responses.py`）的流式实现都是「先
建连拿到状态码、确认 2xx 才提交 `StreamingResponse`」——那个检查点就是唯一
安全的切换点。一旦返回 `StreamingResponse` 就开始出字，之后上游断流、报错，
一律如实透传：半截答案后面再接另一个模型的输出是不可接受的。

- **只切一次**，不做链式兜底（兜底模型的兜底）。兜底也失败就返回它的真实错误。
- 首次尝试失败时其 TPM 预扣已返还，兜底那次以数量为 `0`、但仍绑定原准入
  分钟桶的兼容预留凭据记账，计费不重复且不会把跨分钟结果写入新桶。

> 顺带修复：`/v1/responses`（Codex）此前在生成器内直接开流，上游 5xx 也会
> 回 HTTP 200 + 错误体。现已统一为先查状态码再流。

### 第 2 层 · 熔断（高级，默认关闭）

原模型持续坏时，后续请求**直接从兜底模型出，完全不碰坏节点**（省掉每次都
先白打一遍的延迟）。日常只开第 1 层即可；第 2 层会改变后续整段路由，需在
后台「高级策略」里显式勾选 `circuit_enabled` 才生效。

- **双阈值**：窗口内 `失败数 ≥ trip_fails` **且** `失败率 ≥ trip_rate` 才熔断。
  只看次数会误伤高流量模型，只看比率会被低流量的偶发故障误伤。
- 计数用 Redis 定窗（`INCR` + `EXPIRE`，与 `policy.py` 限流同款），跨副本共享。
  失败率需要分母，所以**成功也要打点**：为配了兜底的模型每请求多一次 pipeline
  （2 命令 1 RTT，约 0.3ms）。未配兜底的模型 `get_config()` 直接返回 `None`，
  **零 Redis 流量**。全程 fail-open。
- 熔断/恢复经 Redis pub/sub 广播到各 gunicorn worker 的**内存副本**，
  热路径只读内存，**零额外往返**。worker 中途重启时启动扫一次 `fb:open:*` 回填。

### 熔断如何恢复

熔断态是一个**带 TTL 的标记，不需要任何人主动清除**：

```
[正常] ──失败数≥N 且 失败率≥P%──> [熔断中 · 冷却 cooldown 秒]
   ↑                                        │
   │                          冷却期内所有请求直接走兜底，不碰原模型
   │                                        │
   │                                标记到期，自然消失
   │                                        ↓
   └── 原模型已恢复 ─────── [下一个请求自己回到原模型] ─── 仍故障 ──┐
                                                                   │
                        该请求被第 1 层当场救走（用户无感）         │
                        失败重新累积 → 再次熔断，冷却时长翻倍 ──────┘
```

**「半开探测」是免费得到的**——不需要探针机制，也不需要后台健康检查线程。
代价是每个冷却周期有极少量请求去踩一下原模型，而它们都被第 1 层兜住了。
这正是两层设计的价值：**第 2 层省算力，第 1 层保体验**。

冷却时长**指数退避**：`min(cooldown_s × 2^(n-1), max_cooldown_s)`，默认
120s → 240s → 480s …… 封顶 30 分钟，避免彻底宕机的节点被反复试探。退避计数
的 TTL 是冷却时长的 10 倍，模型稳定一段时间后自然清零、退避重置。

### 人工介入

- **强制恢复**（模型列表上的 ↺ 按钮 / `POST /api/admin/models/{id}/circuit/close`）：
  清 Redis 标记与退避计数并广播，立即回原模型。运维确认节点修好了、不想等
  冷却时用。
- **强制熔断**（编辑弹窗里的勾选，存 `extra.fallback.forced`）：写在库里，
  **不会自动恢复**，用于计划内维护、节点即将下线。与自动熔断互不干扰。

### fail-open

所有 Redis 操作失败即视为「未熔断」，退化成只有第 1 层即时切换。宁可多打
一次坏节点，也绝不能因为协调层抖动，把全平台流量误切到兜底模型上。这个
best-effort 取舍只适用于兜底状态；`policy.py` 的请求限流属于安全准入边界，
Redis 不可用时会 fail-closed 返回可重试的 `503`。

## 三、配置

存在 `model_registry.extra.fallback`（JSON 列，**无需数据库迁移**）：

```json
{
  "enabled": true,
  "target_model_id": "qwen3.6-35b",
  "circuit_enabled": false,
  "trip_fails": 5,
  "trip_rate": 0.5,
  "window_s": 60,
  "cooldown_s": 120,
  "max_cooldown_s": 1800,
  "forced": false
}
```

保存时校验（`admin.py:_normalize_fallback`，配错直接 400——兜底是故障时的
最后一道保障，宁可保存时拦下）：

- 目标必须存在、不指向自身；
- 必须是**实模型**（不能指向 LTS 虚拟模型：故障时多一层解析即多一层不确定性）；
- 必须与本模型**同 category**（embedding 不能给 chat 兜底）；
- 必须已完成部署配置（`base_url` + `model_api_name`）；
- 不得与目标**互为兜底**（2 元环）。

运行时若目标已下线或配置被改坏，`routing.resolve_fallback_target()` 静默
返回 `None`（降级为「无兜底」），绝不因兜底配置有问题而让正常请求失败。

**与 Key 模型白名单的关系**：兜底目标**不受** Key 的 `models` 白名单约束。
这是管理员在模型层面配置的平台级替代，其对立面是整个请求失败；计费按实际
调用的模型如实记录。

## 四、可观测

不新增数据库字段，**用已有的 `usage_logs.request_id`**（已建索引）：

一次兜底会留下**两条同 `request_id` 的日志**——失败那条 `model_id` 为原模型、
token 为 0（预扣已返还）；成功那条 `model_id` 为兜底模型、正常计费。
**同 request_id 出现两个不同 model_id ⇒ 发生过兜底**，查询与归因天然成立。

- 响应头 `X-Fallback-From: <原模型 id>` 告知客户端；响应体的 `model` 字段
  如实写兜底模型的真名（不伪装），用户从日志即可自查「为什么这次效果不一样」。
- 熔断触发写 `WARNING` 级日志；强制恢复写 `AuditLog`。
- `GET /api/admin/models/circuits` 返回当前熔断中的模型（纯内存读，不查库），
  admin 列表每 15s 轮询刷新徽章。

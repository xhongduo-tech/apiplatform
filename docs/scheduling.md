# 流量治理：限流 + 直连转发（2026-07-18 最终简化版）

> 历史：平台先后实现并移除了三代网关侧调度——「保底-抢占」双档位调度
> （2026-07 初移除）、KV 感知路由与上下文分档（2026-07-16/18 移除）、
> 单队列 FIFO 并发准入（含跨副本排队、心跳防僵尸、ledger 崩溃对账，
> 2026-07-18 移除）。最终结论：**调度权整体归还推理引擎**。vLLM/SGLang 的
> continuous batching 自带「上限 + 内部队列 + KV 准入 + 抢占」，是唯一
> 知道显存真实水位的调度器；网关在其上再做一层准入，要么重复、要么失真。
> 现行方案如下。

## 架构：网关只做三件事

1. **限流**（每 Key RPM/TPM，三档预设见下；每日 19:00–次日 07:30 夜间不限流窗口内跳过 RPM/TPM）；
2. **路由**（虚拟模型解析 + 多节点进程内轮询）；
3. **如实转发**（不压缩、不截断、不改写、不排队、不预检）。

请求经限流校验后**直达推理引擎**。引擎过载时的表现——TTFT 变慢、引擎内
排队、极端时拒绝或断开连接——网关原样透传给客户端，由客户端按错误码退避。

> 唯一例外是**模型兜底**（2026-07-21，见 [fallback.md](./fallback.md)）：仅当
> 节点故障（连接失败/超时/上游 5xx/401/403/404）时切到管理员配置的兜底模型。
> 过载（429）不在其列，仍然如实透传——饱和判定权归引擎的原则不变。

## 限流

每 Key 每分钟定窗计数（Redis 跨副本共享，`app/redis_client.py`）：平台默认
`RATE_LIMIT_RPM`（600）、`RATE_LIMIT_TPM`（6,000,000）；管理员可在
「后台 → 密钥管理 → 并发」按 Key 上调/下调覆盖（留空回落平台默认，保存即时
生效），详见下节「并发档位」。TPM 采用「原子预扣 + 事后校正 + 失败返还」，
详见 `app/proxy/policy.py` 模块注释。所有 Redis 操作**失败即放行
（fail-open）**，协调层抖动不误伤流量。

**高可用（Redis Sentinel，可选）**：配置 `REDIS_SENTINEL_NODES` 后网关经
Sentinel 发现 master，故障切换自动跟随重连；切换窗口（~5-15s）内的限流命令
按 fail-open 放行。部署用 `docker-compose.sentinel.yml` overlay。

## 并发档位：速率闸门 ≠ 容量承诺

平台对外只有三档，全部落在 `settings.rate_limit_presets()`（`/api/public/config`
下发，前端不硬编码）：

| 档位 | RPM / TPM | 落库值 |
|---|---|---|
| 平台默认 | `RATE_LIMIT_RPM` / `RATE_LIMIT_TPM`（600 / 6,000,000） | `null` / `null` |
| 高并发 | `RATE_LIMIT_HIGH_RPM` / `RATE_LIMIT_HIGH_TPM`（3,000 / 60,000,000） | 该数值 |
| 超高并发 | 不限流 | `-1` / `-1` |

RPM 与 TPM 各自独立三态，允许混档（如「RPM 无限 + TPM 限额」）。实现细节
（三态语义、写入层拒绝 `0`、缓存失效、档位反查）见
[TECHNICAL.md 6.4](./TECHNICAL.md)。

**必须说清楚的一件事：这三档不是调度，只是 `policy.enforce_pre` 里的两个
阈值。** 它们决定「这个 Key 每分钟最多被放进来多少」，不决定「进来之后跑多
快」。把某个 Key 升到超高并发，只是拿掉了网关这道限流，**不增加任何吞吐**
——请求照样直达引擎，排在同一个 continuous batching 队列里，TTFT 由引擎的
KV 水位决定。真实并发承载能力始终是：

```
可承载并发 ≈ 引擎准入参数（--max-num-seqs / --max-running-requests）× 节点数
```

因此"给大户开超高并发"这件事**本身不构成容量交付**，它只是把闸门打开；闸门
之后能不能扛住，是下面两节（节点选择、容量与过载）的事。两者顺序不能颠倒：
先确认引擎侧扛得住，再开闸门；否则开闸的结果只是把排队从网关 429 变成引擎
里所有人一起变慢——**限流是保护上游不被单个 Key 打满的公平性工具，不是过载
治理工具**，过载治理只有扩节点和调引擎参数两条路。

**运营闭环**（升档动作的完整链路，缺一环就不闭环）：

| 步骤 | 动作 | 落点 |
|---|---|---|
| 1. 评估 | 该用户的目标 RPM/TPM 是多少，折算成并发请求数 | 用户申请 / 夜间批量登记 |
| 2. 压测 | 确认目标模型在当前引擎参数下的吞吐拐点 | `scripts/calibrate.py`（见下文「兜底压测」） |
| 3. 扩容 | 拐点低于目标就先扩节点或调引擎准入参数 | `extra.endpoints[]` / `--max-num-seqs` |
| 4. 升档 | 再在「后台 → 密钥管理 → 并发」套用档位 | 保存即时生效 |
| 5. 观测 | 次日日报是否出现 `saturation_suspect` | 见下文「结果信号巡检」 |
| 6. 回退 | 若已饱和：扩节点 / 收紧引擎准入 / 引导错峰、夜间批量 | —— |

**与夜间窗口的关系**：每日 19:00–次日 07:30 的不限流窗口内 `enforce_pre` 直接
早退，三档在窗口内**全部等价于超高并发**（且窗口内不做速率计数）。也就是说
档位只在白天有区分度；夜间的天花板永远是引擎容量本身。用量页速率面板会在
窗口内标注「不限流」，不展示数值——避免用户把"未计数"误读成"未调用"。

## 节点选择

多节点部署时在 `extra.endpoints[]` 列出各节点 `base_url`，网关进程内轮询
分发，不依赖外部 LB。不做上下文长度分档、不做超限预检——输入超过节点
`--max-model-len` 时由上游模型直接报错（vLLM 返回 400），网关如实透传。
同一模型请统一按最大所需上下文部署。

## 容量与过载：判定权在引擎

部署引擎时按显存与目标上下文设置引擎自己的准入参数：

- vLLM：`--max-num-seqs`（启动日志会打印 KV cache 总 token 容量与按
  max-model-len 折算的最大并发倍数，按需收紧）；
- SGLang：`--max-running-requests`；
- 拿不准就偏保守：引擎准入偏低只是吞吐略欠喂，偏高会 KV 抢占抖动伤所有
  人的 TTFT。

网关不设并发上限、不排队。极端过载下客户端可能等到读超时
（`UPSTREAM_READ_TIMEOUT_S`，默认 600s）或收到上游连接错误——这是刻意
选择：过载语义完全由引擎表达，网关不代为兜底。

**结果信号巡检**（运营日报，阈值 `OPS_SATURATION_INFLATION_WARN`，默认 4 倍）：
`saturation_suspect`（warning）——某模型高峰小时时延中位数达到低谷小时的
4 倍以上（流式 latency_ms 即 TTFT，引擎积压的征兆是陡增而非渐进）→ 引擎
高峰期饱和。处置：扩节点、下调引擎准入参数收紧其内部队列、或引导高峰
大户错峰/夜间批量。**注意不要用「给大家降档」来救过载**——降 RPM/TPM 只是
把过载从引擎移到网关 429，用户侧同样失败，且伤及未超量的正常用户；
档位是公平性工具，容量问题只能用容量手段解。

**兜底压测**（验证引擎参数是否合理）：

```bash
python scripts/calibrate.py --base http://localhost --model <model_id> \
    --key sk-platform-xxx --levels 1,2,4,8,16,32,64,128 --secs 6
```

输出每档 吞吐/p95/错误 表，吞吐拐点即该节点在当前引擎参数下的真实容量。

## 计量不丢失：取消安全

客户端提前断开流式响应时（OpenAI SDK 收到 `[DONE]` 即关连接属标准行为），
starlette 用 anyio level-cancellation 取消响应生成器——finally 里的每个
await 会再次抛 CancelledError。因此流式 finally 中的上游连接关闭与
`policy.record_tokens`（TPM 差额校正）均经 `app/aioguard.py` 的 `guarded()`
执行：正常路径内联等待，被取消时转入独立 task 后台完成，计量绝不丢失。

## 关键参数（内置默认，环境变量可覆盖）

`RATE_LIMIT_RPM` · `RATE_LIMIT_TPM` · `RATE_LIMIT_HIGH_RPM` ·
`RATE_LIMIT_HIGH_TPM` · `NIGHT_UNLIMITED_START/END` ·
`UPSTREAM_READ_TIMEOUT_S` · `OPS_SATURATION_INFLATION_WARN`
（全部内置于 `app/config.py`，部署无需配置文件）

## 验证

制造高并发占满某模型 → 观察：① 网关不拒绝、不排队，请求全部转发至引擎，
TTFT 随引擎内积压上升；② 429（RPM/TPM 超限）带 `Retry-After`，语义不变；
③ 客户端断流后 usage_logs 仍有该请求的计量记录（取消安全）；④ 次日运营
日报对高峰饱和的模型产出 `saturation_suspect` 告警。

档位链路另测：⑤ 把某 Key 升到高并发/超高并发，其 429 阈值随即改变（无需重启、
不等鉴权缓存 TTL），且**吞吐与 TTFT 不因升档而改善**——这正是"档位只是闸门"
的预期表现；⑥ 夜间窗口内三档一律不触发 429，用量页速率面板显示「不限流」而非
进度条。
